# NegLab

把彩色负片的数字化文件反相成中性、线性的正片。

NegLab 只做一件事：**把反相所需的参数从「凭感觉试」变成「可以量」。**

macOS 12 及以上，双击即可运行的 `.app`，不依赖 Python、Qt 或任何第三方库。
MIT 许可。

---

## 安装

### 方式一：下载预编译版本

从 [Releases](https://github.com/yuyx0407/neglab/releases/latest) 下载
`NegLab-3.0-macos-universal.zip`（约 100 KB），解压后把 `NegLab.app` 拖进「应用程序」。

Apple 芯片与 Intel 机器通用，需要 macOS 12 或更高版本。程序不联网，不写系统目录，
不需要安装 Python 或任何依赖。

本版本未经 Apple 公证，首次打开时系统会提示「无法验证开发者」。两种处理方式：

- 在访达里右键点击 `NegLab.app`，选「打开」，再确认一次；
- 或在终端执行一次：`xattr -dr com.apple.quarantine /Applications/NegLab.app`

### 方式二：从源码构建

```bash
git clone https://github.com/yuyx0407/neglab.git
cd neglab
./app/build_app.sh --install     # 编译并拷到 /Applications
```

只需要系统自带的 clang，不需要 Xcode 工程文件。若只想试编译结果，用 `./app/build_app.sh --run`。

## 使用流程

共四步：

1. 打开负片（拖入窗口，或按 ⌘O）；
2. 定零点：在图上点一下未曝光的片基，或改用自动估计；
3. 解 γ：在几块中性灰上各点一下，按「解算 γ」；
4. 导出。

**γ 对一个「胶片型号 × 扫描链路」只需解一次**，此后每次换卷只重复第 1、2 步。

## 一、它解决什么问题

现有的胶片反相工具（darktable 的 negadoctor、DiVERE、SpektraLab、Negative Lab Pro 等）
算法本身都不差，问题出在参数上：

| 现有工具的做法 | 后果 |
|---|---|
| 把逐通道密度斜率 γ 写成固定常数（negadoctor 硬编码 4.0，Cineon 固定 0.6） | 换一种胶卷、换一家店就不成立 |
| 让用户手动拖滑杆试 | 没有判据，只能「看着顺眼」 |
| 完全闭源 | 无法确知它究竟做了什么 |

本项目实测得到的一个结论：

> 同一批扫描件上，从画面反推得到的 γ 为 0.738（红）/ 1.770（蓝）；
> 从灰阶卡上读出的 γ 为 0.933 / 1.626。**两者相差 0.34 档。**
> 而所有反相方法之间的差异只有 0.1～0.3 档。

换言之，**把参数测准，比更换软件更有价值**。NegLab 就是把这件事做成一个可操作的工具。

## 二、原理

### 1. 密度与透过率

负片记录的是密度而非亮度。密度 D 与透过率 T 的关系为

```
D = −log10(T)
```

因此「把亮度取反」（1 − T）在数学上不成立。正确的反相必须先转成密度、在密度域
处理，再转回透过率。

### 2. 色罩

C41 彩色负片上那层橙色，是品红与黄色染料的固定残留，等于给每个通道垫了一层底。
它的物理后果有两条：

- 蓝通道被压得最重，片基处透过率常常只有 14% 左右；
- 三个通道的感光—显影曲线斜率不同，这个差异就是 γ。

实测某卷真实胶片，片基密度为 R 0.27 / G 0.60 / B 0.85，蓝通道是红通道的三倍多。

### 3. 核心三行

```
Pi_c  = −log10( clip(T_c / T0_c) )        ① 相对零点的密度
L_c   = ( Pi_c − o_c ) / γ_c              ② 逐通道曝光坐标
out_c = 10^( (L_c − L_ref) / 0.6 ) − 1    ③ 反相
```

三个参数的更新频率不同，这是整套方法里最容易被搞混的地方：

| 参数 | 含义 | 多久定一次 |
|---|---|---|
| T0 | 零点，即未曝光片基在密度轴上的位置 | **每一帧** |
| γ | 逐通道密度斜率比 | **一次**，管一个「胶片型号 × 扫描或翻拍链路」 |
| o | 逐通道偏移，与 γ 同时解出 | 与 γ 同步 |

### 4. 如何测出 γ：秩 1 分解

在一段中性灰上（例如灰阶卡的六级灰），设第 k 级的曝光为 L_k，则有

```
Pi_R(k) = o_R + γ_R · L_k
Pi_G(k) = o_G + γ_G · L_k
Pi_B(k) = o_B + γ_B · L_k
```

对下标 k 而言，L_k 是与通道无关的同一个量。因此把 N×3 矩阵去掉每一列的均值之后，
它应当**秩为 1**。做一次奇异值分解即可同时得到：

| 分解结果 | 含义 |
|---|---|
| 第一右奇异向量 γ | 逐通道密度斜率比，即所需的量 |
| 各列均值 o | 逐通道偏移 |
| σ2 / σ1 | 这批点够不够中性，小于 6% 视为合格 |

**不需要知道这些灰块的绝对亮度**，只需要它们确实是中性的。

RawTherapee 的 Film Negative 使用的是同一套数学（它的 Red ratio 与 Blue ratio
即 γ_R/γ_G 与 γ_B/γ_G），只是固定要求用户点两块。NegLab 用秩 1 分解，点几块就吃几块，
每多一块多两组约束。

### 5. 为什么零点必须每帧重定

T0 是「零曝光」的位置，物理上就是未曝光的片基。而多数店扫件为了画面好看，会把图像
裁到正好 36×24 mm，片基、齿孔、边码全部剪掉。

此时只能退而取「画面中最亮的像素」作为替代。它是否真的是片基、是否中性，
取决于那一帧拍了什么。实测在同一卷之内，零点就能漂移 0.37～0.49 档，比所有方法之间
的差异都大。

因此最有价值的一条改进是：**要求店家不要裁到画幅内**。这一步不花钱。

## 三、从冲扫到成品

### 第 0 步：选择数字化方式

决定成败的不是使用什么设备，而是最终拿到什么规格的文件。

| 方式 | 优势 | 代价 |
|---|---|---|
| 店扫（诺日士 HS-1800、易麦康 X5 等） | 平整、均匀、分辨率高、支持 ICE 除尘、速度快 | 默认输出 8-bit、sRGB、裁到画幅内，恰好把最需要的三样全部剪掉 |
| 自行翻拍（相机 + 光源 + 片夹） | 完全可控：16-bit、线性、不裁画幅、一次拍 raw | 需要购置器材，需要处理反光与平整度 |

判断标准是店家能否提供所需规格的文件：能给则选店扫（画面质量更稳定），
不能给则选翻拍。

实测对比：8-bit 店扫件的蓝通道唯一取值只有 89 个（约 5.6 bit）；自行翻拍 raw 转出的
16-bit 线性 TIFF 为 52788 个。相差两个数量级。

### 第 1 步：向店家索要的文件

以下文字可直接复制发送：

```
这卷底片希望尽量保留原始信息，麻烦按下面参数扫描：
① 16-bit TIFF，不要 JPEG
② 线性输出，不要套任何色彩空间或显示曲线
③ 不要反相（按正片模式扫，画面偏橙色是正常的）
④ 关闭所有自动项：自动对比度、色彩平衡、锐化、颗粒抑制
⑤ 最重要：不要裁到画幅内，请把片基、齿孔、边码一起扫进来
⑥ 我拍了一张灰阶卡，请让它与画面用完全相同的参数一起扫出来
```

按优先级争取，拿到哪一步算哪一步：

```
最高   不裁画幅，保留片基     最值钱，且免费
最高   16-bit
高     不反相
高     线性，不套 sRGB
中     关闭所有自动项
```

### 第 2 步：拍摄灰阶卡

只需要灰，不需要 24 色卡。色罩问题是「中性 + 线性」，24 色卡买到的是「颜色像不像」，
属于另一个问题。

| 卡片 | 是否够用 |
|---|---|
| Datacolor SpyderCheckr（48 格） | 够用，自带多条中性列 |
| ColorChecker Classic（24 格） | 够用，底部有一整行六级灰阶 |
| 自己打印灰阶阶梯 | 勉强可用，纸张反光会降低精度 |
| 单块 18% 灰卡 | 不够。能钉住偏移，钉不住斜率，表现为中性对了但亮部暗部仍向两侧偏 |

三个硬性要求：

1. 与画面同卷、同光源、同一次扫描。最省的做法是每卷开头占用一到两格。
2. 卡片必须完整出现在画面内。若店家裁到 36×24 mm，它会被切掉，这是整条流程中最容易断的一环。
3. 灰阶级数应覆盖从片基到接近最大密度的范围。六级够用，十二级更稳。

更换光源（例如从宽带白光换到窄谱 RGB 光源）等于更换链路，需要重新标定 γ。

需要重做 γ 的情形：

| 情形 | 是否需要重拍 |
|---|---|
| 更换胶片型号 | 需要（Gold 200 与 Portra 400 的 γ 不同） |
| 更换店家、更换机器、店家改动设置 | 需要 |
| 更换光源 | 需要 |
| 同型号 + 同店家 + 同批冲洗 | 不需要，γ 不会变 |
| 每卷开头拍一两格 | 属于保险措施，不是数学必需。它防范的是「店家换了药水而没有通知你」 |

### 第 3 步：在 NegLab 中处理

打开 NegLab，按四步操作。

**① 打开负片。** 拖入窗口或按 ⌘O。支持 16-bit 线性 TIFF、8-bit TIFF/PNG/JPEG；
相机 raw（ARW、CR3、NEF、DNG、RAF 等）由系统自带的 Core Image 解码器直接读取。

读取时按位深决定解释方式：16-bit 及以上视为线性，8-bit 视为 sRGB 编码并反解传输函数。
之所以不一律交给色彩管理，是因为扫描件常常不带描述文件，交给色彩管理会「顺手」
再套一次传输函数，逐通道密度斜率就被破坏了，而那正是需要测量的量。

对于 raw，读取时会关闭相机默认外观：对比度曲线、饱和度、高光恢复、局部色调映射、
阴影提亮。这些变换是按通道施加的非线性操作，开启状态下测到的 γ 里会混入相机的
S 曲线，就不再是胶片的 γ。

**② 定零点（每帧都要做）。**

- 画面中有未曝光片基时，按「在图上点片基」，然后在齿孔区或帧边透明条上点一下。
  这是最准的做法，且帧帧独立。
- 没有片基时，使用自动估计（取最亮 0.05% 的均值，先经 3×3 中值滤波去除热噪点）。
  需要清楚它会被「这一帧最亮的东西是什么颜色」带偏。

**③ 解 γ（一次性）。**

1. 按「点中性灰」；
2. 在负片上的灰块中央点击，至少两块，亮度要拉开；
3. 按「解算 γ」。

界面会给出 σ2/σ1：小于 6% 说明这批点足够中性；显著偏大时，换几个位置重点，
或回头检查零点。点错了可以按「撤销」。

批量处理的场合，也可以从命令行完成，见下文。

**④ 导出。**

- **16-bit 线性 TIFF**：这是母版，未套传输函数，可继续在 DaVinci Resolve 或
  Photoshop 中分级；
- **8-bit JPEG / PNG**：已套好 sRGB 传输函数，可直接查看或发布。

预览与导出使用同一个白点（绿通道的 99.9 百分位），避免「所见非所得」。

## 四、常见问题

### NegLab 比 negadoctor 更科学吗

在反相算式上不是。NegLab 用的就是 Cineon 家族那三行；negadoctor 在已知中性灰阶上
误差 0.75 档，同一算式配上准确参数大约在 1.5 档量级。

NegLab 的价值在于参数可以变成测量值。如果零点靠猜、γ 也没有测，它不会比 negadoctor
更好，可能更差；只有在参数给对的前提下才发挥作用。

### 店扫件是 8-bit sRGB 且裁到画幅内，还能用吗

能读入，但信息已经丢失。8-bit 的密度量化台阶约为 0.0248 D，是 16-bit 的约 80 倍粗；
蓝通道唯一取值常常只有 89 个；没有片基意味着零点只能猜。软件的体检面板会直接提示
「某通道唯一值过低」。这种情况下更换文件比更换软件更重要。

### 一定要拍灰阶卡吗

如果不拍，只有两个选择：一是改用 RawTherapee 的 Film Negative（参数一一对应，
但只支持 raw，店扫 TIFF 无法使用）；二是接受 γ 为内置常数或靠自己手搓。
灰阶卡的成本是一两格胶片，是整条链路里性价比最高的一步。

### 灰阶卡需要买 24 色的吗

不需要。色罩问题只需要灰。若目标是「跨卷、跨时间输出同一个颜色」，才需要透射色靶、
光谱实测数据并建立 DCP，这属于颜色管理范畴，与色罩是两个问题。

### 未曝光片基与边码各自的作用

| | 是什么 | 作用 | 是否需要知道胶片型号 |
|---|---|---|---|
| 未曝光片基 | 完全未曝光的透明区 | 光度零点，定义密度轴的原点 | 不需要 |
| 边码（如 FUJI 200、10A） | 片边印制的字符 | 身份识别，用于选择胶片档案与归档 | 它本身就是答案 |

两者不是一回事：片基用于测量，边码是元数据。附带的好处是，片基出现在画面里时，
可以当场判断通道有没有被扫爆。

### Windows 和 Linux 能用吗

核心算法写在 `app/NegMath.m` 中，是一个不依赖任何第三方库的纯 C 文件，
移植到其它平台没有障碍；`tools/` 下的命令行自检同样如此。目前的图形界面与
raw 解码依赖 macOS 的 AppKit、ImageIO 与 Core Image，尚未移植。

## 五、实测数据

| 项目 | 数值 |
|---|---|
| 8-bit 店扫件蓝通道 | 唯一取值 89（约 5.6 bit），密度台阶 0.0248 D |
| 翻拍 raw 转 16-bit 线性 TIFF | 唯一取值 52788 |
| 从画面反推的 γ（红 / 蓝） | 0.738 / 1.770 |
| 从灰阶卡读出的 γ（红 / 蓝） | 0.933 / 1.626 |
| 两者之差 | 0.34 档（方法之间差异仅 0.1～0.3 档） |
| 灰阶卡六点中性残差 | ≤ 0.049 档 |
| 同卷之内的零点漂移 | 0.37～0.49 档 |
| 片基估计偏差一倍导致的输出误差 | 5～10 档 |
| 密度上限取 1.8 时制造的假偏色 | 1.08 档（取 2.5 时为 0） |

### 外部依据

| 本项目的做法 | 依据 |
|---|---|
| Cineon 常量：片基 = code 95、参考白 = 685、0.002 D/code、负片 γ = 0.6 | Kodak《Color and Mastering for Digital Cinema》 |
| 逐通道指数模型 `Pi_c = o_c + γ_c·L` | RawTherapee Film Negative 的源码级模型：`R = R^rexp × rmult`，`rexp = refexp × rratio` |
| γ 一次性、零点每帧 | RawTherapee 官方文档「每卷点一次，可拷贝给同卷其它照片」；作者说明「系数与白平衡是完全不同的东西，系数对整卷不变，白平衡每帧不同」 |
| 在胶卷头几格拍摄色卡 | RawTherapee 作者的建议 |
| 取样点过少会把系数带偏 | RawTherapee 作者：「两点靠得太近时颗粒噪声会引入很大误差」 |

完整的推导与全部实测记录见 `docs/原理与实测.md`，逐条做法的出处见 `docs/参考文献.md`。



零点仍然逐帧自动估计，γ 与偏移取自标定文件。输出 `.tif` 为 16-bit 线性，
其余扩展名输出 8-bit sRGB。

## 七、开发者注记

### 关于 .app 的体积

成品约 170 KB。界面是 AppKit 原生，图像解码走 macOS 自带的 ImageIO 与 Core Image，
数学是一个不依赖任何库的 `.m` 文件。因此不需要打包 Python 解释器，也不需要打包 Qt
（后者会让体积增加三个数量级）。

### CIRAWFilter 的属性名

`CIRAWFilter` 的 ObjC 头文件里写的是 `draftModeEnabled`、`contrastAmount` 等，
但实际实现类 `CIRAWFilterImpl` 使用的是 CIFilter 的 `input*` 命名。照头文件书写的结果是
「生效 0 项、忽略 21 项」，相机外观一项都没有关掉。属性名应当通过运行时反射确认：

```objc
Class c = [f class];
unsigned n = 0;
Method *ms = class_copyMethodList(c, &n);
for (unsigned i = 0; i < n; i++)
    if (strncmp(sel_getName(method_getName(ms[i])), "set", 3) == 0)
        printf("%s\n", sel_getName(method_getName(ms[i])));
```

### 扩展色彩空间不能用于整数位图上下文

`kCGColorSpaceExtendedSRGB` 与 `kCGColorSpaceExtendedLinearSRGB` **只能**配 32 位浮点上下文；
拿它们建 8 位或 16 位的 `CGBitmapContextCreate` 一定返回 NULL。而 Core Image 解码 raw 之后
给出的图像恰恰就是扩展线性 sRGB —— 直接照搬它的色彩空间必然失败。

同族的非扩展版本（`kCGColorSpaceLinearSRGB`、`kCGColorSpaceSRGB`）传输函数完全一样，
`[0,1]` 区间内的数值不会被改动，只是丢掉了超出范围的部分。所以按「源本身是线性的就退到
LinearSRGB，否则退到 sRGB」的顺序挑一个建得出来的空间即可。退错了会把传输函数套第二遍。

### 相机翻拍的 raw 必须先做防削顶补偿

负片上最亮的区域就是未曝光的片基，而相机翻拍通常把曝光给到「片基接近满量程」。
Core Image 渲染成 16 位整数时，超出 1.0 的部分被直接削平 —— 削掉的恰恰是零点要用的那部分。
实测某张 NEF 的红通道有 **12.3%** 的像素在 1.0 以上，于是自动零点被解成 1.00001，
整幅画面崩掉。

因此解码分两趟：先渲染一张四分之一的小图、以 32 位浮点取出真实数值，量出「每像素三通道
最大值」的 99.95 百分位；据此补一个**只降不升**的 EV，把最亮处压到 0.98 以下，再正式渲染。
`inputEV` 的实测行为是精确的：−1 EV 恰好把数值减半。

### 窗口尺寸与内容的循环依赖

`NSWindow` 在内容视图使用 Auto Layout 时，会用内容的**拟合尺寸**去决定窗口尺寸。
一旦内容的宽度和高度互为因果（例如「一行的宽度取决于画布宽度、画布的高度又取决于这行文字
折几行」），Auto Layout 解不开这个环，只会挑一个退化解：把整个窗口缩到刚好装下那行字。
而且这个过程不打约束冲突日志，`contentMinSize`、`setContentSize:`、甚至 `setFrame:`
都会被布局引擎盖掉。

现在的做法是：**顶层四块（画布 / 状态行 / 分隔线 / 检查器）用框架布局**，由根视图的
`-layout` 摆放 —— 窗口尺寸是「因」，各块位置是「果」，因果关系不再成环。检查器内部仍然用
Auto Layout，因为它的宽度是固定的，不会反过来影响窗口。

### 三处「看起来像缺陷，其实是量错了」的地方

- **三通道的经 γ 归一后的曝光坐标绝不能取中位数。** 取了输出就是一张灰图，颜色全丢。
- **跨帧搬运标定时，偏移 o 与 L_ref 是常数，不要做所谓的「平移」。** 代数上
  `L_c − L_ref = L − L0_B` 对三个通道相同，天然中性；每帧的零点通过 `Pi` 自己进入。
  额外加平移反而会引入偏色。
- **用对数衡量「比值的极差」之前，先确认分母不为零。** 片基那一行的输出恰好是 0，
  `log2(0)` 会给出假的天文数字。早期写法据此把 Cineon 在某一卷上的漂移算成 34.8 档，
  真值为 2.4 档。

### 直方图求百分位时的值域

显示映射需要对反相后的输出求百分位。反相输出的量级可以从 0 到上万，而线性透过率
只在 0 到 1 之间。若按固定区间 [0,1] 建直方图，所有大值都会挤进最后一格，
百分位被算成 1.0，整幅画面会被打白。正确做法是先扫一遍确定真实值域，再按值域分箱。
